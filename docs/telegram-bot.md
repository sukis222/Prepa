# Telegram-бот: первый этап

Стек: aiogram 3, Python 3.12+, long polling. Интерфейс преподавателя — сообщения
и клавиатура Telegram. `app.py` содержит Router, `service.py` — независимый от
Telegram диалог, `settings.py` — настройки. Общие схемы используются без копий.

## Запуск и доступ

Установка и Compose описаны в [README](../README.md#запуск). `.env` загружается
через python-dotenv; переменные окружения имеют приоритет. Нужны
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALLOWED_USER_IDS=123,456` и `DATABASE_URL`.
В Compose подключение задаётся через PGHOST/PGDATABASE/PGUSER/PGPASSWORD.
ID — числовые идентификаторы пользователей, не username и не токен бота.
Для открытого доступа задайте `TELEGRAM_ALLOWED_USER_IDS=*`; пустое значение
по-прежнему запрещено. Команда `/id` показывает ID текущего пользователя.

Личный чат и доступ (список ID либо явный `*`) проверяются до чтения состояния.
Профили и запросы читаются из PostgreSQL с фильтром по Telegram ID преподавателя.
Новый преподаватель начинает с пустого списка; демонстрационные профили в БД не добавляются.

## Сценарии

1. `/start`, `/help` — возможности, ограничения и кнопки.
2. `/students` — ваши ученики. `/add_student` или «Добавить ученика»:
   имя, затем класс и экзамен (`9 ОГЭ`, `11 ЕГЭ`). Уровень и цель не запрашиваются.
3. `/lesson` — номера одного или двух учеников. Для каждого по очереди бот запрашивает
   темы через `;`, затем число задач от 1 до 50, не меньше числа тем. Каждый шаг
   подписан именем ученика; классы и экзамены могут различаться. Времени, уровня, ДЗ
   и пожеланий в форме нет.
4. Бот показывает отдельную строку каждого ученика: имя, экзамен, темы и число задач. Только `/confirm` или
   «Подтвердить» запускает подготовку. До подтверждения внешних вызовов нет.
5. `/edit` — темы и число задач последнего индивидуального запроса заново, затем
   подтверждение новой версии. Старый совместный запрос остаётся в архиве; его
   редактирование создаёт новые индивидуальные запросы. Для смены учеников — `/lesson`.
6. `/cancel` отменяет черновик; `/status` показывает текущий шаг;
   `/history` — последние 20 версий; `/result` повторно выдаёт сохранённый файл.
7. Для каждого выбранного ученика создаётся отдельный запрос и отдельный PDF с
   условиями задач, без теории, ответов и ДЗ. Для двух учеников это два независимых
   файла с разными темами и количеством задач. `/result` показывает последний;
   `/history` и `/result N` позволяют получить любой из двух.
   Проверка выполненного ДЗ и приём файлов пока не подключены.

Некорректный ввод сохраняет текущий шаг. `/lesson` и `/edit` заменяют незавершённый
черновик. `/start` и `/help` его не сбрасывают. История содержит запросы,
а не факты проведения занятий или готовности документов.

## Подключение оркестратора

Внедрить `PreparationBackend` в `DialogService(teacher_ids, backend)`. По умолчанию
backend отсутствует: запрос сохраняется в PostgreSQL, генерация не выполняется.
В real-режиме используется общий клиент OpenRouter.

Рабочий real-режим вызывает `SourceSelectionBackend.prepare(...) -> TaskWorksheet`.
Профили и подтверждение проверяются на сервере; источник «Решай Онлайн» возвращает
полные условия и рисунки. Модель выбирает только ID, а содержание копирует код.
`SourceDocuments.worksheet` собирает отдельный PDF для каждого ученика.

Вызов backend ограничен 170 секундами, worker — 210; отдельный вызов модели — 120.
При ошибке источника, недостатке подходящих задач или сборки PDF готовый файл не
объявляется. В лог попадает только класс ошибки, без ключей и ученических данных.

Старый генератор `RealBackend` с теорией/заданиями/reviewer сохранён для разработки
и автономных тестов, но приложение его не выбирает. Demo остаётся явно отмеченным
тестом интеграции с синтетическими условиями.

## Ограничения

- Сессии, ученики и подтверждённые версии сохраняются в PostgreSQL. Каждый шаг,
  включая незаконченный ввод ученика или запроса, восстанавливается после перезапуска.
  История в интерфейсе показывает последние 20 версий, БД хранит все подтверждённые версии.
  При сбое записи бот не подтверждает сохранение; повторите ввод после восстановления БД.
- Старые запросы деморежима в памяти прежнего процесса автоматически не переносятся.
- Polling последовательный (`handle_as_tasks=False`); при включённом деморежиме
  подготовка выполняется отдельным фоновым worker через очередь PostgreSQL. Запрос и состояние сохраняются одной транзакцией
  до вызова бэкенда; строки преподавателя блокируются для защиты от повторных подтверждений.
  Один poller на токен. Для прямого внедрения backend без очереди автовосстановления нет.
- В прямом режиме без очереди автоматических повторов нет. После ошибки можно создать новую версию через
  `/edit`. Отмена черновика не отменяет уже начатый вызов оркестратора.
- При сетевом сбое возможна частичная выдача файлов. В режиме очереди готовые результаты
  сохраняются и доступны через /result.
- Нет OCR, проверки ДЗ и обновления прогресса.
- Лимит формы — 50 задач на ученика. Если выбранный источник не содержит нужного
  числа подходящих задач, подготовка завершается сообщением об ошибке: новые условия
  для заполнения недостатка не сочиняются.

Тесты `tests/test_bot.py` работают без Telegram и БД. Справка транспорта:
[aiogram Router](https://docs.aiogram.dev/en/latest/dispatcher/router.html) и
[Dispatcher polling](https://docs.aiogram.dev/en/latest/dispatcher/dispatcher.html).

## Режимы генерации и фоновая очередь

`PREPARATION_MODE=off` (по умолчанию) сохраняет только запросы.
`PREPARATION_MODE=demo` включает `DemoBackend` и `DemoDocuments`: никаких платных
моделей и никакой оценки физики. Любые темы заполняются синтетическими заглушками,
а результат — один PDF с пометкой «ДЕМО». Это проверка интеграции, не материал для урока.
`PREPARATION_MODE=real` подключает OpenRouter, поиск текстовых источников ФИПИ,
составителей теории/заданий и reviewer. Выдаёт один PDF с условиями задач. Требуется API-ключ;
модель и ограничения описаны в [инструкции](openrouter.md).

Подтверждение всех выбранных учеников, отдельные снимки проверенных профилей
и отдельные задания в `preparation_jobs` сохраняются одной транзакцией. При сбое
записи второго запроса первый также не сохраняется; черновик доступен для повтора. Фоновый worker не блокирует обработку сообщений.
Он проверяет `LessonPackage`, совпадение контекста и сохраняет комплект с файлами
перед отправкой. Ученический renderer получает только `package.for_student(id)`.

- `/result` или кнопка «Результат» — состояние и файлы последнего запроса.
- `/history` — нумерованные последние 20 версий; `/result 1` выдаёт выбранную версию.
- `/retry` или `/retry 1` — явный повтор только неудачного задания в том же режиме.
- `/edit` создаёт новую версию; старые файлы не изменяются.
- После переключения режима старый запрос без задания не генерируется автоматически;
  подтвердите новую версию через `/edit`.

После аварии задание возвращается в работу по истечении 4-минутной аренды, не более
трёх захватов. Токен захвата запрещает старому worker записать или отправить результат
после перехвата задания другим worker. Подготовка с документами ограничена 180 секундами.
Режим очереди сохраняется: real-worker не подхватывает demo-задания и наоборот.
Если доступ преподавателя отозван, worker не вызывает backend и не отправляет файлы.

Ошибка Telegram не удаляет результат: `/result` повторяет выдачу сохранённых байтов.
Автоматическая доставка не имеет гарантии exactly-once; после сбоя между сохранением
и отправкой используйте `/result`. Долговременный архив за пределами последних 20
версий и хранение больших файлов в object storage — отдельные задачи. Сейчас файлы
(до 10 MB каждый) и комплект хранятся в JSONB вместе с заданием.

### Подключение настоящих модулей

В composition root `bot/app.py` режим `real` выбирает `RealBackend`,
`OpenRouterLLM`, `FipiMaterials` и `LatexDocuments`; `demo` сохраняет заглушки.
CLI принимает off/demo/real. Сценарий диалога, очередь, хранилище результатов
и отправка Telegram остаются общими. Безопасную компиляцию PDF выполняет `LatexDocuments`.

Backend получает подтверждённый `LessonBrief` и снимок разрешённых профилей и возвращает
валидный `LessonPackage` с новым review. Renderer преподавателя получает весь комплект,
renderer ученика — только `StudentLesson`. Результат renderer — `Attachment(name, bytes)`;
настоящая реализация должна безопасно компилировать PDF и разделять обычный текст/LaTeX.
Приём/проверка выполненного ДЗ остаются неподключёнными; режим real их не имитирует.

### Проверка

Автономно: `pytest tests/test_preparation.py` (без Telegram и PostgreSQL).
Отдельно: `python integration_tests/check_demo_workflow.py` при PGDATABASE=prepa_test*
и настроенных PG*. Скрипт применяет миграции к отдельной тестовой базе и проверяет
очередь, восстановление аренды, ограничение повторов, версии и изоляцию преподавателей.

В Telegram: `/add_student` → имя → `9 ОГЭ`; затем `/lesson` → номер ученика
→ темы → `4` → `/confirm`. В real дождитесь одного PDF; в demo — одного помеченного PDF,
проверьте `/result`, затем `/edit` и новую версию. После `podman compose restart`
проверьте `/students`, `/history`, `/result 1`: файлы должны совпадать побайтово.

Для двух учеников: `/lesson` → `1,2` → темы первого → `5` → темы второго → `8`
→ общий просмотр → `/confirm`. Незавершённый ввод второго ученика восстанавливается
после перезапуска. До общего подтверждения ни один запрос не запускается.

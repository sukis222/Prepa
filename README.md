# Prepa

ИИ-помощник репетитора по физике для подготовки учеников 9–11 классов к ОГЭ и ЕГЭ.

Prepa — Telegram-бот для репетитора. Текущий сценарий: выбрать одного или двух учеников, отдельно указать каждому темы и число задач от 1 до 50, подтвердить запросы и получить каждому компактный PDF с условиями задач и, при наличии разборов в источнике, второй PDF с решениями. Уровень, время занятия и домашнее задание не запрашиваются.

## Статус проекта

В рабочем сценарии используется один LLM-агент отбора исходных задач. Отдельно реализованы составитель теории, составитель заданий и проверяющий материалы; текущий бот их не вызывает. Telegram-бот на **aiogram 3** поддерживает добавление и выбор учеников, согласование и подтверждение запроса, правки с новой версией, отмену и историю запросов. Ученики, запросы и черновики сохраняются в PostgreSQL. Есть Dockerfile, Compose с PostgreSQL 17 и начальная SQL-схема. В режиме `PREPARATION_MODE=demo` работают заглушки оркестратора и документов: фоновая очередь PostgreSQL, один демонстрационный PDF и повторная выдача через `/result`. В `PREPARATION_MODE=real` подключён согласованный источник «Решай Онлайн» для ЕГЭ по физике: программа ищет исходные задачи по теме, а модель OpenRouter выбирает их ID. Код переносит условия и имеющиеся рисунки в один PDF без переписывания моделью. Если исходных задач недостаточно, бот сообщает доступное количество; новые условия не генерируются. Свободный диалог оркестратора и проверка выполненного ДЗ ещё не подключены. [Настройка реальных моделей и ограничения](docs/openrouter.md).

Реализован поиск задач по теме в открытом банке ФИПИ (`task_bank/`): по коду КЭС или названию темы он находит задачи ОГЭ и ЕГЭ и выдаёт их текстом со ссылками на рисунки. Ответов и решений банк не публикует. [Описание поиска](src/prepa/task_bank/README.md).

Текущая реализация этих трёх агентов ещё требует входные материалы (`materials`); это ограничение предстоит убрать согласно выбранному сценарию без библиотеки. Найденные в банке ФИПИ задачи можно передать агентам как `materials` через `task_bank.to_material`. [Описание реализации](docs/content-agents.md), [критерии качества](docs/content-quality.md).

## Основной сценарий

1. «Добавить ученика»: имя, затем класс и экзамен — например, `9 ОГЭ` или `11 ЕГЭ`.
2. «Новое занятие»: номера одного или двух учеников из списка.
3. Бот называет первого ученика и просит описать желаемые темы и задачи: можно указать часть ЕГЭ, номера заданий, сложность и пожелания. Затем спрашивает число задач от 1 до 50.
4. Если выбран второй ученик, бот отдельно спрашивает его темы и число задач.
5. Преподаватель видит оба индивидуальных запроса с именами и подтверждает их одной кнопкой.
6. Для каждого ученика независимо: поиск исходных задач → отбор ID моделью → перенос условий, формул и рисунков → компактный PDF с задачами подряд и жирными номерами: зелёный — первая часть, оранжевый — вторая. Ссылки на источники, вводные сайта и служебные маркеры рисунков в ученическом PDF скрыты; оригиналы сохраняются без изменений. Сообщение с результатом подписано именем ученика.
7. `/history` показывает оба запроса; `/result N` повторно выдаёт нужный файл, `/result` — последний. «Правки» создают новую версию последнего индивидуального запроса.

Бот предназначен преподавателю: ученику достаточно передать полученный PDF.
При выборе двух учеников создаются два независимых запроса. Ученические PDF не содержат решений. Для каждого запроса дополнительно выдаётся PDF преподавателя, если в источнике найдены подходящие решения; отсутствующие разборы отмечены явно. Это объяснения сайта, не официальные решения ФИПИ; требуется проверка преподавателем.
Старые совместные комплекты остаются доступными в истории. В подтверждении показываются имена, экзамен, темы
и число задач — без внутренних ID и технических параметров.
Уровень ученика и параметры времени пока остаются внутренними значениями старого
контракта; их удаление из общих схем — отдельная миграция. Старый генератор теории и практики сохранён как отдельный модуль для разработки;
рабочий режим бота использует отбор исходных задач и не вызывает этот генератор.
Проверка выполненного ДЗ и свободный разговор с LLM пока не подключены.

Рабочий источник — `SOURCE_PROVIDER=reshai`. Исходные условия читаются с сайта, рисунки проверяются и копируются, публичные страницы кэшируются локально. В живой проверке получены 30 задач по термодинамике и собран PDF из 20. Для узкого запроса «циклы, вторая часть» найдено 14 полных условий в пределах ограниченного поиска; это не размер всего банка. Если заданий недостаточно, новые условия не генерируются. Подключение ОГЭ к этому источнику и задачи с содержательными HTML-таблицами пока не поддерживаются.

`SOURCE_PROVIDER=local` и `SOURCE_CORPUS_PATH` оставлены для явного автономного запуска с проверочным набором; автоматической подмены реального источника старым набором из четырёх задач нет. Лимит вызова модели — 120 секунд. Подробности — в [настройках источника](docs/openrouter.md).

Основная локальная рабочая копия находится в корне этого репозитория. Прежняя папка `local-run/` сохранена как резервная и исключена из Git; команды запуска выполняются из корня.

## Агенты

1. **Оркестратор-собеседник** (`orchestrator`) — обсуждает с преподавателем темы, цели и формат занятия, получает контекст ученика через инструменты. После согласования вызывает остальных агентов, направляет замечания на исправление и собирает комплект материалов.
2. **Составитель теории** (`theory`) — готовит объяснения, формулы и разобранные примеры по согласованным темам.
3. **Составитель заданий и ДЗ** (`assignments`) — составляет практику на урок и индивидуальное домашнее задание, ответы и решения.
4. **Проверяющий материалы** (`reviewer`) — проверяет подготовленные теорию, задания и ДЗ до выдачи ученику, возвращает замечания составителям.
5. **Проверяющий ДЗ ученика** (`homework_checker`) — проверяет выполненные решения, объясняет ошибки и предлагает результаты для обновления базы знаний ученика.

Собеседник и оркестратор объединены: согласование и запуск подготовки используют один контекст диалога. Это уменьшает число вызовов и передачу данных между агентами. Порядок этапов, подтверждение тем и предел повторных исправлений задаются кодом оркестратора. Отдельный планировщик урока не нужен.

Чтение и обновление базы знаний ученика — общие инструменты, а не отдельные агенты. База знаний содержит сведения об ученике и его прогрессе; собственной библиотеки учебных материалов нет: задачи по теме ищутся в открытом банке ФИПИ модулем `task_bank/`. Все агенты находятся внутри одного серверного приложения и могут использовать одну модель с разными инструкциями. Преподаватель проверяет и утверждает результат.

## Структура репозитория

Рабочий код есть в bot/, agents/theory/, agents/assignments/, agents/reviewer/, schemas/ и task_bank/. В db/ реализован репозиторий PostgreSQL; migrations/ содержит версионированные SQL-миграции.

```text
src/prepa/
├── bot/                aiogram, ученики, согласование запросов, версии и история
├── agents/
│   ├── orchestrator/   диалог, согласование и управление подготовкой
│   ├── theory/         теория и разобранные примеры
│   ├── assignments/    задания на урок и ДЗ
│   ├── reviewer/       проверка подготовленных материалов
│   └── homework_checker/ проверка выполненного ДЗ ученика
├── documents/          сборка содержания в LaTeX и компиляция PDF
│   └── templates/      будущие шаблоны оформления документов
├── schemas/            общие форматы данных для команды
├── task_bank/          поиск задач по теме в открытом банке ФИПИ
├── tools/              чтение базы знаний ученика и сохранение результатов
├── db/                 таблицы и доступ к базе
└── llm/                реализованный бесплатный клиент OpenRouter и настройки вызовов
migrations/            начальная SQL-схема PostgreSQL
Dockerfile                контейнер бота
compose.yaml           бот и PostgreSQL с постоянным volume
data/
└── demo/               вымышленные ученики и примеры заданий и решений
tests/                  проверки поведения программы
pyproject.toml          настройки Python-проекта
.env.example            образец настроек без секретов
```

Веб-интерфейс и отдельное HTTP API в первой версии не требуются. Интерфейс преподавателя — сообщения и кнопки Telegram. Для будущего оркестратора выделен `PreparationBackend`. Получение сообщений реализовано через long polling, без публичного веб-сервера.

Сборка PDF — обычная программная операция в documents/, дополнительного агента для неё нет. Шаблоны задают оформление, агенты возвращают содержание. Сгенерированные .tex, PDF и промежуточные файлы создаются во время работы в output/ и исключены из Git. Каждая подготовка и версия документа получает отдельные рабочие файлы.

## Этапы реализации

### Этап 1. Запрос через Telegram

Реализуем bot/, llm/ и оркестратора: запрос, уточнение тем и подтверждение. Контекст связываем с пользователем Telegram и выбранными учениками. Для начала используем вымышленные профили из data/demo/.

### Этап 2. Подготовка содержания

Подключаем theory/, assignments/, reviewer/ и homework_checker/. Согласуем форматы в schemas/, включая состав комплекта, идентификатор подготовки и версию. Чтение профиля и сохранение подтверждённых результатов реализуем в tools/. Преподаватель согласует темы до подготовки материалов.

### Этап 3. LaTeX → PDF → отправка

Добавляем шаблоны и компиляцию в documents/. Проверяем русский текст, формулы и разделение ученических материалов и ответов преподавателя. При ошибке компиляции бот сообщает о неудаче; готовым считается только успешно собранный PDF. Правки сообщением относятся к конкретной подготовке и версии документа.

### Этап 4. История и запуск в контейнерах

PostgreSQL через db/ сохраняет профили, запросы и состояние диалогов. Compose запускает два сервиса: бот и PostgreSQL с постоянным volume. В real-режиме LaTeX собирает один PDF с условиями задач. Инструкции запуска — ниже.

Проверки в tests/ добавляются вместе с соответствующей логикой, начиная с первого работающего сценария.

## Папки, которые добавим по необходимости

| Папка | Когда нужна | Пример |
|---|---|---|
| migrations/ | При создании и изменении структуры базы | Добавление поля целевого экзамена |
| docs/ | Когда README станет недостаточно | Описание форматов и инструкции по разработке |
| evaluations/ | При сравнении качества моделей | Одинаковые запросы по физике и предметные оценки |
| scripts/ | Для повторяемых служебных операций | Загрузка демонстрационных учеников |

docs/ уже содержит описание реализованных агентов и критерии качества. Остальные папки добавляются по необходимости. tests/ проверяет поведение программы; evaluations/ будет оценивать качество ответов моделей. Успешная компиляция PDF не подтверждает правильность физики.

## Предлагаемые технологии и настройки

- Python — бот, агенты и сборка документов в одном приложении.
- aiogram 3 / Telegram Bot API — сообщения, кнопки, long polling и отправка файлов.
- PostgreSQL — база знаний учеников, выданные задания, решения и результаты проверок.
- OpenRouter — вызовы моделей по API, общий клиент для агентов.
- LaTeX с поддержкой русского текста — PDF; начальный вариант движка в настройках — XeLaTeX.
- Podman Compose — запуск приложения с LaTeX-движком и базы.

pyproject.toml задаёт Python 3.12+. Для реализованных агентов используется Pydantic 2; дополнение dev содержит инструменты тестирования и проверки кода. Конкретную LLM выберем по результатам сравнения на примерах по физике.

Настройки в .env.example: TELEGRAM_BOT_TOKEN, TELEGRAM_ALLOWED_USER_IDS, POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, OPENROUTER_API_KEY, OPENROUTER_BASE_URL, OPENROUTER_MODEL, DATABASE_URL и LATEX_ENGINE. Бот читает настройки Telegram и PostgreSQL. .env не публикуется. Для демо используются вымышленные ученики.

## Совместная разработка

Перед параллельной разработкой команда согласует форматы `StudentProfile`, `LessonBrief`, `Theory`, `Assignment`, `Homework`, `ReviewResult`, `HomeworkSubmission`, `HomeworkCheckResult`, `LessonPackage` и результат сборки документа. Изменения выполняются в отдельных ветках и объединяются через pull request.

## Запуск

### Быстрый запуск через Compose

Установите Docker Desktop (или Podman по [инструкции](docs/containers.md)).
В каталоге проекта создайте настройки только при первой установке:

```bash
cp .env.example .env
```

В `.env` заполните `TELEGRAM_BOT_TOKEN` (от BotFather), `POSTGRES_PASSWORD`
и `TELEGRAM_ALLOWED_USER_IDS` (числовые ID через запятую либо `*` для доступа всем).
Для проверки полного демосценария установите `PREPARATION_MODE=demo`:
один демонстрационный PDF без вызовов моделей. Значение `off` сохраняет только запросы.
Для настоящей генерации задайте `PREPARATION_MODE=real`, `OPENROUTER_API_KEY`
и бесплатную `OPENROUTER_MODEL` по [инструкции](docs/openrouter.md).
Real выдаёт PDF с условиями и, при наличии подходящих опубликованных разборов, отдельный PDF с решениями. В контейнере установлен XeLaTeX; при локальном запуске нужны XeLaTeX или Tectonic и соответствующие LATEX_ENGINE/LATEX_FONT.

```bash
docker compose up --build -d  # PostgreSQL, миграции и бот
docker compose logs -f bot   # логи; Ctrl+C завершает просмотр
```

В Telegram: `/start` → `/add_student` → `/lesson` → `/confirm`.
В деморежиме бот пришлёт файлы; `/result` выдаёт их повторно, `/history` показывает
версии, `/edit` создаёт новую версию. `/id` показывает ваш Telegram ID.

```bash
docker compose restart  # перезапуск с сохранением данных
docker compose down     # остановка и удаление контейнеров, БД сохраняется
```

Данные находятся в volume `prepa_postgres_data`. **Не используйте `down -v`**:
это удалит БД. После перезагрузки macOS сначала выполните `podman machine start`,
затем `docker compose up -d`. Не запускайте одновременно локальный бот с тем же токеном.

Подробнее: [контейнеры и перенос данных](docs/containers.md),
[сценарии бота и подключение реальных модулей](docs/telegram-bot.md),
[структура БД](docs/database.md).

### Локальная разработка без контейнера бота

Нужны Python 3.12+, работающий PostgreSQL и `DATABASE_URL` в `.env`.
В Compose база подключается через PG-переменные; порт БД на хост не публикуется.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m prepa.db.migrate
python -m prepa.bot
```

Автономный пример трёх агентов и тесты:

```bash
python -m pip install -e '.[dev]'
python examples/content_agents.py
pytest
ruff check .
ruff format --check .
mypy
```

Автономный пример использует записанные ответы и не обращается к реальной модели.
В режиме `real` бот вызывает OpenRouter и проверяет содержание; настройки
передаются и в контейнер. В real-режиме LaTeX собирает один PDF с условиями задач. Не путайте успешный
запуск автономного примера с предметной проверкой настоящей модели.

Поиск задач обращается к сайту ФИПИ и запускается отдельно:

```bash
python -m prepa.task_bank --exam ege --topic 1.1.5 --limit 5
```

## Проверка результата

- Правильность физических условий, ответов, единиц измерения и решений.
- Соответствие заданий уровню ученика и цели занятия.
- Соответствие материалов согласованным темам и формату занятия.
- Время подготовки с учётом проверки и правок.
- Учёт результатов предыдущего занятия.
- Проверка выполненного ДЗ с привязкой к ученику и исходным заданиям.
- Компиляция PDF с русским текстом и формулами, отправка файла и пересборка после правок.

## Оформление и отбор

Условия и рисунки не генерируются моделью. Модель выбирает ID, учитывая свободное описание, разнообразие и порядок от простых задач к сложным. Код фильтрует часть и номера по карточкам источника, отсеивает текстовые численные клоны и ставит первую часть перед второй. Порядок сложности внутри части — оценка модели, не объективная шкала.

Разборы копируются только для отобранных задач, с ограничением 25 секунд. Проверка адреса и чисел отсекает явные несовпадения, но не доказывает корректность физики. Сбой второго PDF не отменяет ученический. Общий лимит фоновой подготовки — 270 секунд, аренда задания — 5 минут; один вызов модели по-прежнему ограничен 120 секундами.
